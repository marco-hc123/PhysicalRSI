Interpretation limits:
- Candidate generation and admission are separate from physical execution; rejected source has unknown native score, not zero.
- These API totals cover System2 proposal generation only. Native evaluations use fixed routes, without high-level System1 API calls. Local DINO/pi05 inference uses compute time, not zero overall resource cost. Do not interpret this pilot as whole-Agent or cross-project token savings.
- The pickup parent was authored for this study; pi05 is a separate pretrained capacity reference, not an editable parent or equivalent action API.
- RGB pickup geometry uses an assumed table height and nominal object dimensions. Classification also has task-specific perception assumptions. Zero improvement does not identify System2 itself as the cause.
- Five development and five heldout layouts per task are a small pilot; selecting a best development candidate is optimistic and requires the reported heldout check. Each policy-layout pair has one native rollout, so simulator/planner variation is not independently estimated.
- No automatic claim of cross-task skill reuse or complete multi-round self-improvement. Only within-task feedback conditions were controlled.
- Scoring, action budgets and native task physics were preserved. Native steps include terminal hold; completed API calls do not prove delivery/lift.
- Preparation failures and the postprocessing repair are preserved separately. No task score was invented or changed.
- Generated public-configuration layouts are not a claim of matching the entire official benchmark distribution.
