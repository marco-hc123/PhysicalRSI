baseline 是基线提示生成的代码候选，不是 pi05 神经父策略；augmented 也不是人工修好的答案。三者分别列出，避免混淆。
前一步完整记录仍保存在 result/30_system2_lab_diagnosis/20261104_v1 与 result/29_system2_feedback_api/20261104_v1，本归档的 predecessor-index.json 给出连接关系和报告校验和。

1. 本轮完成了什么
本轮把此前已保存的 6 个 System 2 候选接入原生 RGB 仿真，和保留的 pi05 父策略在相同的 5 个历史诊断布局上执行，共 7×5=35 个有效测试。
35 个原生结果均经过正常终止、布局身份、评分、进程退出及证据文件校验；保留 105 段三视角视频。
本轮没有重新生成候选，没有训练或更新模型权重，没有执行新一轮策略选择。pi05 仍是保留策略。
“仍保留 pi05”在此表示本轮按诊断协议没有进行替换，不表示选择器在看到本批新分数后拒绝了更高分候选。
本轮新增付费 LLM API 调用为 0，新增付费 API 费用为 0 美元。已有候选的历史生成费用不重复计入本轮。
本轮为服务器上的仿真实验；不是实际机器人实验，也不是完整 RoboDojo benchmark。
版本恢复依据已有冻结记录：Python 3.11.17、Isaac Sim 5.1.0、PyTorch 2.7.0+cu128；267 项 simulator 包与 232 项 policy 包的版本对应，741 个固定运行/源码文件经过校验。41 个检查点文件、15369 个场景文件和 10691 个技能实现文件的校验记录均保留。
环境并非所有条件都能声称与历史机器完全相同：CPU/内存由原先 16 核/128GiB 变为 8 核/64GiB；历史 ffmpeg 可执行文件的精确版本没有记录。本轮使用冻结 imageio-ffmpeg 0.6.0 包内的 ffmpeg 7.0.2，并完成实际编码/解码验收。上述差异不能掩盖，也不能直接作为策略得分变化的原因。
冻结 policy 环境存在已记录的 rerun-sdk 对 NumPy>=2 的元数据声明与 NumPy1.26.4 固定版本冲突；本轮没有为消除声明冲突而升级包，采用实际导入、推理和原生执行验收。包版本复原不等于所有可选模块都已经兼容验证。

详见 case-study-augmented1-layout4.json、ordered-call-traces.csv 和带时间索引的关键帧。此例展示的是阶段进展，不是完整任务成功或已经通过独立验收。

3. 评分具体是什么意思
原生 classify_objects 评分代码使用 15、40、100 三个阶段阈值；输出明细将其归一化到 0–1，_result.json 的总体 Score 则是均值乘 100。
此处采用 transition 累进评分，记录已经到达的评分阶段，不保证最后一帧仍满足该阶段的所有条件；15、40、100 不能相加为 155 分。
阶段得分要求一整类物体进入相应篮筐、满足高度条件、篮筐中没有混入其他类别，并满足夹爪打开要求。完整任务成功还有三类归置及机械臂回到原位等条件。
因此，发出抓取命令、夹爪闭合、完成一段移动或尝试放下某个物体，都不自动等于获得分数或完成任务。
部分分可以证明评估器的部分任务条件成立，但不能替代完整 success。
依据：analysis/reference-contract/classify_objects.py、reward_manager.py、func_parser.py、eval_env.py。

每个候选的隔离进程保存了按数值 call id 排序的调用及返回，分析没有按随机文件名推断执行顺序。
scene/reobserve 的输出、目标机械臂、位置和四元数、规划器拒绝、夹爪命令以及原生终止分别记录于 actor-diagnostics.csv 和原始过程文件。
无碰撞路径失败由 trusted primitive 返回 primitive_error=no_collision_free_path，执行适配层将它转换为 RuntimeError。候选是否继续调用，可由后续 call id 直接核对。
本批 baseline 在首次 approach 被拒绝的比例为 12/15；augmented 为 0/15。
已完成的 approach 调用数分别为 9 与 50。这表示部分候选执行到了更后面的动作阶段，并不等于这些动作都完成了抓取。
本批有 5 个候选在原生 1100 步预算结束时仍有动作未完成，被正常关闭 actor channel。其自然终止的任务结果有效；这类取消不等同于启动环境异常或 API 通信丢失。
未完成调用的部分动作可能已执行，日志中的 completed primitive action_steps 只计已返回的调用，是相关执行量的下界，不能用它精确反推全部保持步数。
另一个独立停止类型出现在 augmented_3：5 个布局均完成 3 次 approach，随后读取抬升后的场景并正常 return，没有发起移向篮筐的第 4 次 approach，也没有规划拒绝或耗尽原生步数。对应已完成原语为 635 或 655 步。它不能被归到“全部路径规划失败”或“全部动作超时”。
模型返回 null、actor 状态 completed 与任务 success 是不同层次的事件，报告未将它们混为一谈。

5. 当前能回答“错误来自哪里”到什么程度
已经明确：本轮首个 pi05 启动尝试缺少 ffmpeg 命令入口，属于环境部署问题。该次尝试没有策略推理，也没有有效评分，已排除并保留原始证据。入口修复后，视频编码和解码测试通过，随后才执行有效测试。
已经明确：对于记录了 no_collision_free_path 的调用，失败信息到达了候选执行边界；不能再把这些具体案例描述为“失败信息全部丢失”。
已经明确：部分候选在规划拒绝后返回，另一些执行更久而触及原生步数上限。这是不同的停止原因，需要分别修正和验证。
新定位的具体不匹配：augmented_3 要求同类别物体的观测 Z 比原来升高超过 0.025m，才继续移向篮筐。释放版 RGB Reader 则用类别 HEIGHT 与固定桌面平面计算 Z，标定后的 ray 仍接收这一指定平面高度，不是测量物体的真实抬升。对本批 5 份原始返回值逐项计算，满足候选 lifted 条件的对象数全部为 0；其中有的目标类别检测消失，有的仍被检测到但没有动态高度。源码紧随其后的 return 与观察到的停止位置一致。
这是一处本批生成候选与当前感知接口能力的不匹配。不能由这项检查失败断言“物理上一定没抓起”，也不能泛化为 PhysicalRSI 核心的普遍错误。这里没有注入新的分支探针或修改候选，判断依据是保存的源码和返回值；详见 lift-gate-diagnosis.csv/json 与 reference-contract/released_rgb_reader.py。
尚不明确：某个目标拒绝究竟由目标/姿态不可达、机械臂选择、坐标标定、碰撞约束或规划器搜索限制造成，现有日志不足以唯一归因。
尚不明确：更好的中间动作主要来自反馈内容、接近高度、目标选择、机械臂选择中的哪一项。候选同时改变多项逻辑，本批不能给出单变量因果结论。
例如 baseline_1 与 augmented_1 在 layout0 的首次目标高度相差 0.13m，XY 位置也相差约 0.232m；在 layout4 还改变了机械臂，XY 目标相差约 0.420m。first-target-contrasts.csv 保存了完整参数，编号配对只是候选编号对照，并非匹配随机种子的单变量实验。
新的 RGB 场景读数也可能与前一步离线探针输入不同，不能把旧目标的规划成功率直接套用到本次新对象、新机械臂或新状态。
本批测试的是冻结的 PhysicalRSI 核心、原生仿真适配层、技能实现、候选源码和配置组合；不能据此判定官方所有版本的 System 2 都有同一种错误。

6. 感知、几何与视频证据的边界
候选读取的场景来自 RGB Reader 和记录的相机标定；尺寸来自固定类别配置，姿态中还存在近似项。它们不是原生评分器的物体真值。
Reader 每次按类别与 X 坐标重新编号对象，这些名称不是跨帧稳定的跟踪 ID；某个对象从识别结果消失不能单独证明它已被放好。已用 backend 源码核对这一点。
本批 cuRobo 碰撞检查使用冻结的机器人/桌面模型，没有完整物体真值碰撞几何。因此“规划器返回路径”也不等于已经证明真实物体接触和抓取质量。
actor 到布局的关联采用保存的初始 RGB 场景与布局类别/XY 的唯一近邻对应，并单独记录距离、间隔及合格标志。布局真值仅用于事后分析，没有输入候选。未合格的关联数为 0，此类条目保持未知。
视频关键帧必须标注 condition、layout、camera 与编码视频时刻。编码时长不直接等于物理仿真时长，也不等于完整墙钟。
视频可展示运动、接触和放置现象；任务得分仍以原生 _result.json 和校验后的 episode receipt 为准。

7. 用量与时间
本批有效的 7 组运行墙钟合计 109.34 分钟，范围包括策略服务启动、仿真执行、清理和证据核验；各组详见 cohort-summary.csv。
该合计不包括先前下载、安装、失败部署尝试、报告制作和资料传输时间。
pi05 内部记录 5500 次 update_obs_batch、110 次 get_action_batch 和 10 次 reset；这些是本地策略服务交互，不能当成 110 次付费 LLM 请求。
候选仿真调用 primitive RPC，也不能把它们记为外部 LLM Token 消耗。本批是执行验证，不能单独用来得出跨项目 Token 节省比例。
本次 CPU/内存配置与历史服务器不同；环境元数据保留实际配置。不能把跨机器墙钟差异全部归因于算法。

8. 下一轮实验建议（本批没有执行）
实验 A：先验证感知能力契约。以 augmented_3 为固定候选，只处理其依赖动态 Z 的 lift gate，保持目标选择、机械臂、规划器、布局和 1100 步不变。原样候选与单处机制消融配对，或另设有可靠抬升证据的修正版。验收分别看是否继续到放置、物体是否真实离台、是否触发误放，以及原生得分。单纯删除检查后能够继续不等于抓取验证正确；仿真真值如用于诊断只能作为离线评估证据，不能偷偷输入候选。随后应在生成反馈中明确每个观测字段的来源、近似和不可观测项。
实验 B：动作目标与规划契约。处理变量一次只改变接近高度、四元数、机械臂或目标位置中的一项；保持同一初始状态、对象、规划器、碰撞模型和随机种子。验收指标为规划是否成功、实际关节/末端位姿误差、是否执行到目标，以及原生任务得分。优先复查本批失败的精确目标。
实验 C：失败后的有界恢复。固定同一候选、同一原语和 1100 步预算，只改变规划拒绝后直接 return 与有界重规划/重新观测的处理。验收指标包括明确终止原因、恢复次数、实际剩余步数、异常、部分分及完整成功率。
实验 D：预算瓶颈诊断。固定候选及布局，单独比较原始 1100 步与预先规定的诊断预算；扩展预算结果单列，不能冒充原 benchmark 提升。若证实受限，再优化路径/动作数量，并回到原始预算验收。
实验 E：小规模独立布局。先审计历史曝光，再冻结 5–10 个未用于候选开发的新布局，比较保留 pi05、未修改候选和单变量修正版；完整报告成功数、得分、故障、调用量和墙钟。
若继续研究反馈内容本身，应增加 Token 预算匹配的反馈对照，保持模型、生成次数、输出预算、下游执行及缓存统计相同。
