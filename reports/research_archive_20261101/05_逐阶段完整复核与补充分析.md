复核日期：2026-11-01。本文补足主报告中展开不足的早期验证、接口实验、失败批次、对照口径和负结果解释。所有数字来自已保存实验，不新增 API 或仿真。主报告负责研究主线，本文负责回答“每一步为什么做、实际测到了什么、不能推出什么”。

## 1. 先把研究中的六类证据分清

| 证据层 | 对象 | 可以回答 | 不能回答 |
| --- | --- | --- | --- |
| CPU 软件验证 | fixture、单元测试、快照和 quota | 软件契约是否按预期工作 | 真实模型或机器人是否成功 |
| 静态请求审计 | 实际构造器与合成 observation | 哪些字段使提示词变长 | 实际计费 Token、API 时延、抓取能力 |

| 原生 System 1 | RoboDojo、技能、Agent | 本环境下的动作、评分、Token 与计时 | 作者完整榜单或等条件跨项目因果效应 |

## 4. 固定输入 API：80 次和 120 次分别回答什么

### 4.1 80 次的设计、原始记录与格式失败

来源：80 次 summary（归档路径：`../sources/local_history/03_api_experiments/summary.json`；完整原件见原资料包或实验室档案）、80 条调用表（归档路径：`../sources/local_history/03_api_experiments/all_calls.csv`；完整原件见原资料包或实验室档案）、[分组复算](../../reports/evidence/tables/early-api-groups-reviewed.csv)、[降幅复算](../../reports/evidence/tables/early-api-reductions-reviewed.csv)。

模型为 `qwen3-vl-plus`，2026-10-27 执行，temperature=0、thinking=false、非流式、最大输出 512。图片是 640×480 的五个合成场景，机器人关节状态为零，没有 RoboDojo 动作。80 次实验请求与此前 2 次连接 smoke 分开：80 次 HTTP 全成功、usage 80/80、无自动重试、无截断，合计输入 854,246、输出 16,129、总 Token **870,375**。38 条请求记录到缓存命中。

80 次并非一个同质的 40 对主实验：包括两 composition 的 40 次、22 operation pilot 的 10 次，以及看过 pilot 后补充 schema 约束的 30 次。pilot 的 projected 契约通过 0/5，unprojected 1/5；HTTP 200 与 JSON 合法不等于能交给执行器的计划合法。两个诊断标签各出现 8 次，可能重叠，不能相加成 16 个不同失败。

| 子实验 | projected / unprojected 调用 | 输入降幅 | 总 Token 降幅 | 请求时长降幅 | 契约结果 |
| --- | --- | --- | --- | --- | --- |
| 两 composition | 20 / 20；5 输入×4重复 | 30.28% | 28.76% | −0.79% | 20/20 与 20/20 |
| 22 operation pilot | 5 / 5 | 67.53% | 66.84% | 25.95% | 0/5 与 1/5 |
| 22 operation + schema | 15 / 15；5 输入×3重复 | 67.34% | 66.88% | 21.22% | 15/15 与 15/15 |

降幅统一定义为 `100×(1−projected组均值/unprojected组均值)`，不要混用“逐对百分比的平均值”。两 composition 的 Token 明显减少，但请求均时从 8.488 秒变成 8.555 秒，**没有获得时延改善**。较大的 operation 目录精简后，schema 组请求均时从 10.882 秒降到 8.573 秒。按五个合成输入聚类的探索性 bootstrap，schema 组均值节约约 2.309 秒、95% 区间约 1.143–3.416 秒；这不是机器人闭环加速的区间。

每条图像输入报告 302 Token，已经包含在 input 内。不同 tokenizer 的文本估计与供应商 input 减 image 的结果也并不总一致，说明包装和分词口径确实重要。此实验固定了调用数，因此不能证明减少了调用频率。schema 是观察 pilot 后改的，结论要标为探索性协议修订。

### 4.2 120 次是更宽的合成输入覆盖，不是 120 个机器人场景

来源：历史审计快照（归档路径：`../sources/local_history/lab_h100_audit_20261029/lab_snapshot.json`；完整原件见原资料包或实验室档案）、[原样摘要提取及来源时间](../../reports/evidence/tables/historical-api120-summary-extract.json)。

设计为 20 个新合成场景×2目录条件×3重复=120 请求。历史 summary 记录 120 次 HTTP/JSON/contract/预设能力标签均通过，总输入 2,184,396、输出 20,201、总 Token **2,204,597**，41 条缓存命中，无截断和自动重试。未精简/精简各 60 次，平均输入 27,437.3 / 8,969.3，总量 27,598.92 / 9,144.37，请求时间 14.432 / 9.864 秒；对应输入降低 67.31%、总量降低 66.87%、请求均时降低 31.65%。

与 80 次 schema 组相比，输入/总量降幅近似稳定，而时延降幅从约 21.22% 变为 31.65%。后者可能受输入分布、网络、排队、缓存、输出和服务状态影响；没有同时随机交叉控制这些因素，不能解释为模型越来越快。

本版证据更新：2026-11-01只读取回并复核实验室120份原始响应、40份请求、120份逐调用元数据及326项历史manifest；哈希和usage一致。旧版仅有历史审计摘要的限制已经闭合。具体复算、分场景数据与边界见全主机总览§5.3（归档路径：`07_全主机实验总览与详细结论.html`；完整原件见原资料包或实验室档案）。这仍是合成输入API实验，不是机器人成功率。

### 4.3 三种“省 Token”不能混成一个结论

静态约 27% 是代理 tokenizer 的 composition 文本差异；固定输入约 67% 是合成图+22 operation 的实际 API 输入差异；原生约 80% 是另一版目录/模型与环境下的自身消融。这三组的分母、目录和模型不相同。它们共同支持“目录内容影响输入规模”，但不构成随阶段递增的改进曲线，更不是 A/B 跨项目节省百分比。

## 5. 云端部署与最小闭环：每个通过意味着什么

完整目录映射见 [42 个云端批次覆盖表](../../reports/evidence/tables/all-cloud-batches-coverage.csv)。部署分为三个验收层：设备/渲染可用、原生场景有效、策略得到原生结果。前一层通过不能代替后一层。

Run06/07 验证 L20 的 CUDA、Vulkan 和项目源码版本，依赖安装在项目隔离路径。Run08 的 RGB smoke 得到 640×480 非恒定图像，红绿方块和球体正常渲染，约 2.5 GiB 的采样显存属于简单场景，不能估算完整双 VLA 的容量。此前缺少图形库和 GL dispatch 配套问题的失败记录保留；修复采用项目本地图形库，不改系统 NVIDIA 驱动。

Run09/10/13 下载并验证官方 manifest、分片哈希、两套发布权重、OpenPI 推理源和代码技能。下载不是训练；分片数量或文件数量也不是实验数量。Run11/15 完成仿真和 policy 两个独立 Python 环境，解决版本/资源绑定；最终运行用的是固定权重。某个环境启动失败只说明该启动条件不完整，不能据此宣布模型能力不行。

Run12 的前三次场景预检依次出现缺 `h5py`、缺 x5 `curobo.yml`，第三次通过稳定布局、机器人状态与三相机 RGB 检查。目标指令为把 mint green scissors 抬高 10 cm。此时还没有运行策略，`robot_task_success` 为未知。

Run14 的两次早期尝试没有有效原生结果（一条 client exit=2，另一条 exit=0 但找不到预期结果），不能记作两次正常零分 episode；后续 fixed pi05 获得原生结果但没有完成目标。Run16 验证 sparse 路线的独立加载与运行。Run17 经启动失败后完成实际 Agent API—技能—原生结果闭环。最小闭环的意义是接口连通与结果可追踪，不是已经复现作者成功率。

来源主要为 `sources/06…17*` 的可读副本及无损文本索引；具体原始状态路径逐一列在覆盖表。运行环境、策略资产和兼容适配不能只靠一张成功截图来证明。

## 7. 原生目录消融：成本效应清楚，质量收益没有建立

来源：[目录消融表](../../reports/evidence/tables/catalogue_ablation.csv)、主报告§10.2。

5 个布局×3重复×2条件=30 个逻辑案例，实际 native 29 个，未进入 native 的失败仍保留在意向尝试分母中。精简组成功 5/15，完整组 6/15；不能把后者改成 6/14 来美化结果。输入总量 173,262 / 875,052，输出 13,306 / 13,918，总量 186,568 / 888,970；cached 均为 0，输入减少 80.1998%、总量减少 79.0130%。

### 8.1 typed API 修订并没有证明格式或成功率提高

两个历史失败输入×3重复×原始/typed 两版本=12 次 replay。原始 6/6、typed 6/6 均通过当时格式检查，因此并未建立“typed 修复了原始失败率”的证据。两组总 Token 分别 75,132 与 73,995，差值涉及输入/输出格式变化，不能视为通用节省。

typed 另做 3 个原生布局，均正常完成但 0/3 成功。它们是额外路线，不可替换原始 Agent 正式参考，也不可把 replay 的 12 次算成 12 个机器人任务。Run21 新发生 7 个 native（4 个原始扩展+3 typed）与 19 个 HTTP，总 Token 236,110；19 已包含上述 12 次 replay。

## 9. 失败审计、原生评分与 sparse memory 的验证

### 9.1 一致性审计排除了哪些解释

Run22 检查 21 条既有记录，无新增 API/native。选定的 25 项源文件检查和 6 项 simulator 检查通过，发布内容与场景资源未发现该审计定义下的不一致。它降低了“随意用了错误版本或错误对象资产”的可能性，但检查清单不是穷尽证明，不能保证与作者所有硬件、训练数据和运行栈完全等价。

旧运行的最后机器人状态在最后动作确认之前，且未保留最终全部物体的精确 transform，不能事后凭该状态断言物体已入篮。内部 detect/predict 门禁也不等于任务真实评分。这解释了为什么后来加入只读的原生物体位置诊断。

### 9.3 sparse 的失败不能解释成“根本没读历史”

来源：memory-validation（归档路径：`../sources/24_steps23_20261030T013742Z_v3/memory-validation.json`；完整原件见原资料包或实验室档案）。两个任务的 sparse 路线分别有 220 条 history materialization、5 次 empty-history episode start、5 次 sparse reset，真实过去帧读取验证通过。另有 6 个已核验快照、11 个 runtime reset 和 58 次不可变读取，属于运行生命周期记录，不是 11 个任务。

### 9.4 Run24 v1/v2 的测量故障怎样处理

### 10.1 Token 分解为什么改变“差距”的解释

`total=input+output`；cached 是 input 的子集，reasoning 已在 output 中则只分析其占比，不再相加。定义 `uncached input+output=total−cached_input` 只是一个去除缓存输入的规模指标，不是美元、计算量、能源或服务延迟。

A 对应任务中 cached 占 input 约 97.3%–98.2%，B 普通分类约 35.9%、语言分类 0。A 的总输入规模很大，但其大部分被标记为缓存。总 Token 比值 888–3050 因而与去缓存指标比值 27.59–75.88 同时成立。缓存不等于“没有历史”或“完全免费”，两家供应商的收费和执行方式也不同。

比较机制的合理层次是：代码与官方说明支持 A 持续短动作生成/审阅、B 把执行移交本地技能；实测支持 B 所测参考每例只发生一次 HTTP、API 输入约 11.5k；但没有证据把跨项目总差距按百分比分摊给目录、频率、模型或缓存。模型推理配置、分词、任务时长和成功率都是未控制因素。

### 11.1 集成与接口失败先于两轮正式结果

Run25 的一个真实 integration 提案输入 318,818、输出 4,781，总量 **323,599 Token**、HTTP 98.35 秒。随后开发 2 个 VLA 回合、父/候选配对验证共 2 个回合完成集成，保留父策略。多次初始化/路径/元数据修复是工程接续，不是多个独立被采用的候选。

Run26 另有提案输入 3,629、输出 27,578、总量 **31,207**、HTTP 442.45 秒。完成 10 个开发回合与 5 个父验证，候选一开始读取场景后把 `basket_1` 当整数解析，抛出 `ValueError`。候选有 1 个已完成 scene-inspection primitive、没有 motion/gripper，属于 1 个中止尝试；没有有效最终评分，0 个提交 round。该次停止流程记录的 4,879 秒是特定尝试墙钟，不是全部 System 2 时间。

Run27 人工修复键解析并在 CPU 检查 named/empty/underscore/repeated-category 等契约。新增 API/native 均为 0，原失败被重现，修复示例通过检查，且未把人工修正版偷换成正式改进候选。`no_path` 应作为可恢复规划结果，transport error 应保留为致命通信错误，畸形 key 应在运动前拒绝。

Run28/29 继续进行 CPU scene gate；named 输入导致拒绝。Run29 已获得第一轮有效记录，第二轮发生契约中断；它的既有证据后来复用。Run30 的父策略 admission 失败，随后登记 inspection-policy bridge，明确重绑定资源、提示词和依赖。不能把这些不同 runtime 绑定描述成从头到尾完全相同的策略哈希链，也不能把它们全部叫成模型推理失败。

### 11.2 正式规则、两轮结果与复用关系

Run23 的预注册为 hybrid、最多两轮、每轮一个候选，开发/验证各 5 个布局；`minimum_vla_score=0.6` 是 normalized 平均 partial score 阈值，不是“60% 全任务成功率”。`minimum_gain=0`、`maximum_regression=0`，平分容差 `1e-10`，平分仍保留父策略。这些是本次注册的选择配置，不宣称与作者所有历史实验参数完全一致。

Run31 最终完成两轮，开发中普通 pi05 平均得分均为 0，sparse 为 0.27 / 0.11，后两项是部分分数。每轮父/候选验证各 5 个，均 0 分、0 成功，两轮都 `retain_parent`。没有强行选择新候选。

40 个逻辑开发/验证记录中，最终续接复用 30 个、只新增执行 10 个；此前支付过的 proposal 在续接时没有再请求。两正式提案分别 24,707 / 26,363，总计 **51,070 Token**、HTTP 合计约 741.56 秒。加上失败提案为 82,277；再含 integration 提案为四个唯一提案 **405,876**、HTTP 1,282.36 秒。它们有包含关系，不能算 `51,070+82,277+405,876`。

formal 提案的输出占比较高，与在线 System1“输入目录占比较高”的形态不同。减少在线高层调用并不保证离线改进也便宜。记录的 native batch 时间约 9,920.78 秒有自己的批次范围，不与 proposal、wrapper、恢复时间无条件叠加成一个总墙钟。

### 11.3 为什么“给两轮机会”没有变成连续修同一个错误

两正式请求的 `current_code` 和 `memory` 都为空；各有 10 条 VLA 开发反馈，但主要诊断字段为动作数与 step limit。上一候选的逐次 RPC 异常没有作为后续输入。父策略被保留后，下一轮仍从保留父策略出发，所以生成器不一定会看到前一份失败程序。

候选都没读取传入 memory；第二个候选只写入三个常量，而该执行分支返回 policy、未回传变更字典。由此应检查“提供了什么、候选读了什么、执行后收回什么”，不能看到函数参数有 memory 就宣称跨轮记忆已生效。这些结论严格限于已测分支，不代表整个 PhysicalRSI 所有 memory 实现。

## 12. 独立验收、恢复和扩展任务分别检验什么

Run34 的独立最终验收对象是最终保留的 **pi05**，普通分类和语言分类各 10 个新布局，全部 1100 步、0 分。没有重新运行一个完整高层 Agent；父策略与最终选择行为相同，只有一组 20 个 rollout，不能写父/候选各 20。语言分类为事先登记的绑定迁移，无新训练。与此前开发布局不交叉，不代表证明不在发布权重训练集里。

## 13. 时间与生命周期成本：把计算放到本地不等于消失

参考 Agent 分类 reset-to-result 约 236.53 秒，API 17.40 秒；语言分类约 214.76 秒，API 12.27 秒。API 占约 7.36% / 5.71%，其余有本地 policy、native 控制和未归属时间。区间无观测重叠后计算的剩余项仍不能命名为 GPU 推理或渲染瓶颈，需要更细 instrumentation 才能归属。

在其他工作完全不变、无等待重叠这一理想假设下，即使把 API 时间降为 0，按这两个均值算的 reset-to-result 上界加速也仅约 1.079 / 1.061 倍。这个算术例子用于解释低占比，不是新测得的优化效果，也不包含冷启动。它说明只优化 Token 未必改变主要墙钟。

Run35 三对冷/连续执行的平均 reset 为 231.92 / 236.71 秒，没有整体加速证据；另有一次预热。两种完整批次的 wrapper 包含不同工作量，不能相除当加速。所有正式配对都失败且到 1100 步；指令、state、composition、operations 对应，但 RGB 没有一对逐像素相同，缓存也未清空。

应同时列三层成本：每个 episode 的在线规划 Token；本地技能推理、动作与仿真时间；离线 proposal、开发验证和失败修复。生命周期可写 `总开销=一次性准备+离线改进+Σ在线执行`。发布模型的训练成本和作者开发成本未知，本研究没有把它们补成零。只有明确质量与成本单位后，才有意义讨论离线改进通过多少次复用摊薄；目前没有 System2 得分提升，不给一个臆造的“回本次数”。

## 14. 机制诊断：沿失败链逐级解释，避免跨级结论

来源：[verified controls](../../reports/evidence/tables/verified-control-results.json)、主报告§9、[规划表](../../reports/evidence/tables/planning_feasibility.csv)。

Run36 v3 的 8 个预登记对照加 1 个动态映射补测，合计 9 尝试：5 个正常结束均 0 分、1 个类别异常、3 个 tracking 中止，后 4 个评分未知。v1/v2 的准备文件不构成另一组完成实验。

原程序入篮判断使用约 ±0.2m 的宽范围，相当于40×40cm；所查接口篮界约20×15cm。布局2原版把待处理对象跳过，0 approach/gripper、0 primitive motion。缩小边界后 dense 条件产生5个approach、4个gripper请求及2次no_path，累计947个已完成 primitive step，但仍0分。说明边界确实控制了动作是否被尝试；没有证明动作完成了目标。

轨迹 thin 在部分条件把长序列缩短，但布局2在34步出现类别异常，布局0在45步被tracking guard中止。短运行属于异常提前结束，不能作为“动作执行快几十倍”。有效比较应先要求同一任务完成语义、相同目标、同样终止规则。

24 次离线规划固定初始关节状态，8 条件×3seed：一个目标抬升20cm为0/3，15/10/5cm各3/3；另外两个右侧目标左臂0/3、右臂及匹配姿态3/3。它定位到高度、用臂/姿态约束，但 `no_path` 不是数学不可达证明，planner success 也不是机器人实际到位，更不是抓取。

动态类别补测消除了一个过早的类别解析障碍后，34步仍触发tracking；对象名字不是稳定物理身份。感知 bbox/位置、目标与仿真对象的对应应继续验证，不能把只读 ground truth 提供给策略再宣称仍是同一视觉任务。下一轮应按“解析合法→路径可行→指令被执行→稳定到位→闭合夹取→离开支撑面→入篮→原生评分”的阶梯验收。

## 15. 全阶段账目与可复现边界

## 16. 本轮复核后的研究结论与最有价值的下一步

已测事实是：高层技能复用使所测 Agent 的在线语言接口负担较小；目录投影在自身实验中降低输入；完整墙钟主要还受本地执行及生命周期成本影响。跨项目总 Token 差距很大，但缓存、模型、成功率与任务条件不同，尚不足以得到等质量效率提升倍数。System2 确实完成两轮，得分未改善并保留父策略；独立验收和机制对照支持继续研究动作契约与反馈，而非继续只增加同样请求次数。

下一轮先离线完善 named-category、motion/approach 完成确认、超时、no_path 和 memory 回传契约，确保失败在运动前可诊断。然后冻结父策略和布局，给 System2 的候选输入补充真实当前代码、上一失败程序、结构化RPC失败及动作完成信息；保持同模型、思考设置、预算、开发/验证布局、评分与选择规则不变。最后仅将通过CPU与原生开发门禁的候选放到少量新独立布局，预先定义原生success/partial score、异常率、反馈完整率、Token、API时间和完整墙钟，平分保留父策略。具体变量和验收列在完善性与未知项（归档路径：`06_报告完善性检查与未知项.html`；完整原件见原资料包或实验室档案）。
